## 2. 推荐视觉方向：明亮、清晰的教学工作台

采用白色内容区、冷灰背景和蓝色主操作，以清晰的任务组织、排版和反馈体现设计品质。

### 2.1 基础视觉规格

| 用途 | 建议值与用法 |
| --- | --- |
| 页面背景 | `#F5F7FB`，工作区背景 |
| 内容表面 | `#FFFFFF`，列表、正文和任务工作区 |
| 主文字 | `#172B4D`，标题、正文与关键数据 |
| 次级文字 | `#607089`，时间、来源和辅助说明；实现时检查对比度 |
| 主操作 | `#2563EB`，发布、继续学习和提交等动作 |
| 边界 | `#E2E8F0`，必要的分组与表格分隔 |

正确、待处理、异常分别使用语义绿、琥珀和红，始终配文字。蓝色不用于表达“已掌握”。

- 字体使用系统中文无衬线字体，优先 `PingFang SC / Microsoft YaHei / Noto Sans SC / system-ui`，不依赖在线字体服务。
- 正文和主要控件以 16px 为基准，辅助说明 14px，区块标题 20px，页面标题 28px；投屏关键结论可到 32px。重要依据不得藏在小字中。
- 公式与作答使用清晰的数学排版，去掉贯穿界面的手写、楷体风格。确需渲染复杂公式时采用可本地离线运行的成熟方案，不为装饰引入依赖。
- 常规控件圆角 8px，独立面板 12px；遵循嵌套关系，不给所有元素同一种大圆角。
- 阴影仅用于浮层、抽屉或确有层级关系的区域；普通列表主要依靠留白和细分隔线。
- 常用按钮高度 40–44px，手机触控目标至少 44px；一个区域突出一个主要动作。
- 桌面采用约 216px 导航、约 64px 顶栏，内容宽度约 1280–1360px；正文保持合理行长。
- 优先验证 1440×900、1366×768、390×844，以及浏览器 125% 缩放。
- 图标有必要才使用，一套即可；可采用本地化 Lucide，避免 emoji、随意自绘装饰图标和在线 CDN 依赖。

### 2.2 移除的旧风格

- 奶油纸张背景、手写作业式整页包装，以及作为界面主题的红笔连线。
- 到处重复的“样例”药丸、说明小字、技术统计和常驻演示控件。
- 标题、导航、正文缺少层级的密集小字布局。
- 等尺寸指标卡铺满首页、装饰渐变、发光、漂浮和没有操作用途的图表。

保留一处持续可见的“虚构样例演示”说明。例题、历史记录和学生新提交仍须明确区分。

## 3. 按真实教学动作组织产品

本轮推荐以**课后学习跟进**作为完整场景。当前资料是历史样例，因此将教师起点称为“学习回顾”，不虚构新作业批次、发布时间或已经发生的教学效果。

教师操作链：

```text
查看学习情况 → 核对重点问题 → 确认跟进安排 → 查看学生完成情况 → 给出反馈
```

学生操作链：

```text
看到待完成任务 → 理解学习目标 → 阅读指定材料 → 保存/提交作答 → 查看反馈和下一步
```

继续使用本地演示身份，任务状态与提交真实保存。切换身份明确标注“演示教师/演示学生”，不能表述为已实现真实认证。

本轮不以正式登录、复杂教务、消息通知、课表或签到作为前置条件。

### 3.1 教师工作台

主导航调整为：**教学工作台、学习跟进、学生情况、教学材料**。

首页突出实际需要处理的工作：进行中的安排、待查看的学生提交，以及最近的学习回顾。无记录时显示下一步入口，不能生成假的待办数量。

```text
┌ 智慧学伴   七年级数学 / 当前班级          演示教师  切换视角 ┐
│             │ 教学工作台                                 │
│ 教学工作台  │ 查看本次学习情况                 [查看学情] │
│ 学习跟进    │                                            │
│ 学生情况    │ 需要你处理                                 │
│ 教学材料    │ 学生 / 跟进目标 / 当前状态 / 下一步操作       │
│             │                                            │
│             │ 正在进行的学习安排                         │
│             │ 目标、涉及学生、完成情况     [查看进展]      │
└─────────────┴────────────────────────────────────────────┘
```

“学习回顾”先显示共性问题、信息不足和建议处理对象，学生名单作为进一步查看，而非进入后立即展示整个数据表。当前范围始终可见，规则、出处和数据质量放在就近的可展开位置。

### 3.2 学生证据与准备跟进

从具体问题进入学生详情，同屏读清学习要求、观察事实、判断边界和建议。教师检查记录后，再确认需要安排的学习活动。

```text
返回本次学习回顾      学生07 / 去括号

当前观察：6 条有效记录中答对 2 条，漏乘反复出现

┌ 作答与对照讲解                    ┬ 跟进安排草稿            ┐
│ 原题、记录来源、错误步骤          │ 目标：检查分配律的使用   │
│ 解释与正确过程                    │ 材料、验证活动、提示     │
│ 明确示例与实际作答的区别          │ 学生、完成条件、观察点   │
└──────────────────────────────────┴─────────────────────────┘
                                      [保存草稿] [确认发布]
```

- 建议先生成草稿，由教师确认目标学生、内容和验证活动后发布。
- 对多名学生可以安排同一项活动，按实际依据分组；不要求给每个人生成不同文案。
- 教师在学生详情中查看或预览任务，不出现能替学生提交的答题按钮。
- 发布后提供“预览该学生任务”，携带该学生和该任务上下文，不能调用会重置到固定学生的全局角色开关。

### 3.3 学生任务工作区

学生默认进入“我的任务”，辅助入口为“学习回顾”。完成前不必先浏览知识点目录或全量材料库。

```text
我的任务
去括号：检查括号内的每一项
教师安排 / 完成要求 / 当前进度

阅读讲解  ─  完成验证  ─  查看反馈

┌ 当前步骤的主要内容                         ┬ 任务说明    ┐
│ 完整材料正文 / 验证题 / 分步提示            │ 学习目标    │
│ 作答区域                                   │ 为什么安排  │
│                                            │ 完成条件    │
└────────────────────────────────────────────┴─────────────┘
                               [保存进度] [提交本次作答]
```

步骤条只对应真实任务阶段，不用作装饰。

- 选择选项保存为草稿，明确点击提交后才交卷。
- 提交前不下发参考答案，提交成功后才返回允许展示的解析。
- 刷新后恢复任务和草稿；提交后可查看自己的作答、规则反馈与教师处理状态。
- 可以自报“已阅读”，但不能把它等同理解或掌握。
- 教师要求继续尝试时新增作答记录，原提交仍可回查。

### 3.4 跟进进展与成果

教师查看某项安排中谁尚未开始、谁在进行、谁已提交，点入提交后确认完成或要求再试，并给出说明。

报告作为回顾和任务的成果，沿用相同学生、范围与版本。JSON/CSV 保留为次要操作，教学页面不出现数据表名、JSON 字段或数据库术语。

## 4. 后端模块与最小业务状态

保持 FastAPI 单体与 SQLite，不引入微服务、Redis 或前端构建框架。先把现有职责拆清，再增加最小任务闭环。

| 模块 | 拥有的职责 | 前端对应动作 |
| --- | --- | --- |
| 教学上下文 `context` | 演示操作者、班级、当前回顾范围、查看权限边界 | 进入班级、切换演示学生、延续上下文 |
| 学习内容 `content` | 要求、知识点、材料、题目与版本、可用性 | 阅读材料、选择跟进内容 |
| 学情分析 `insights` | 有效记录、覆盖、个体和班级摘要、学习回顾 | 查看本次学情、核对证据 |
| 跟进安排 `followups` | 草稿、发布、目标学生、冻结内容和进展 | 准备、确认发布、查看进展、关闭 |
| 学生任务 `submissions` | 待办、开始、阅读确认、草稿、提交、尝试历史 | 继续学习、保存、提交 |
| 教师反馈 `reviews` | 查看原答、完成确认、继续尝试、反馈记录 | 查看提交、给出下一步 |
| 成果 `reports` | 共用分析和任务结果生成报告与导出 | 学习回顾、导出成果 |

### 4.1 状态与事实边界

- 安排状态：`draft → published → closed`。
- 每位学生的任务状态：`not_started → in_progress → submitted → completed`。
- 教师可由 `submitted` 标记为 `needs_retry`，学生再次提交时生成新的 attempt。
- 发布时冻结材料、题目、建议依据与版本。发布后的调整不能悄悄影响学生正在完成的任务，需要新增版本或新安排。
- 客观题反馈使用明确规则。任务完成、答对一道题、阅读材料都不能直接等于“掌握度提高”。
- 历史诊断维持原记录范围；新提交单独保存，只有明确纳入新观察窗口并重新分析后，才能生成新诊断。
- 发布、提交、反馈具备版本检查和重复请求处理；过期操作返回冲突，保存失败返回 503 并还原内存。

### 4.2 数据与迁移

当前 `StudyStore` 把练习事实放在 `reports['study-practice']`；上游掌握度重建会清空 `reports`。接入新任务前，先把事实迁出缓存。

- 优先在 `study_store.py` 以子类扩展独立、带 schema 版本的教学状态，贯通快照、读取、备份与恢复，继续复用上游 SQLite。
- 新增回顾、安排、草稿、提交和反馈的领域模型及请求/响应 schema。
- 旧练习迁为“已知最后选项”，不补造提交时间、次数或教师安排。迁移可重复执行，且只发生一次有效转换，保留恢复办法。
- 新状态即使执行报告缓存清空仍然存在。
- 本地演示身份集中在依赖中解析，检查任务所属班级与被分配学生。将来可以替换为 `get_current_user()` / `require_roles()`，不能把前端隐藏按钮当权限控制。
- 正式赛事资料适配放在数据源边界，体验不要求先上传正式数据。不引入真实学生个人信息，不上传到外部模型。

### 5.1 后端建议结构

```text
server/app/

  services/study/     对应业务用例与查询
  models/study.py     回顾、任务、提交、反馈
  schemas/study.py    请求与分角色响应
  study_store.py      教学状态存储和迁移
```

模块数量服从职责，不为每个简单函数单独建文件。

### 5.2 前端建议结构

保持原生 ES modules，不增加构建依赖：

```text
web/
  app.js             装配
  bootstrap.js       加载上下文和初始化
  api.js             请求、超时、错误
  navigation.js      回顾/学生/任务上下文与返回位置
  ui.js              DOM、搜索、焦点与动效工具
  views/teacher.js   教师任务页面
  views/student.js   学生任务页面
  styles.css         新视觉体系
  index.html         新外壳与入口
```

可复用现有 `preserve()`、支持 composition 的 `searchField()`、可取消的 `reveal()`、材料正文和证据展示逻辑；去掉旧纸张主题与数据目录式导航。

新前端不再依靠全量 `window.XB` 运行，按页面和任务查询。

旧 `/api/study/*` 保留为本地样例兼容适配层，调用同一分析服务。新学生接口不下发其他学生数据或未提交答案。兼容接口继续明确为本地演示接口，不作为真实账号部署方案。

## 6. 动效与操作细节

- 常用反馈 120–180ms，页面、抽屉切换 180–240ms，以 transform/opacity 为主。
- 任务详情进入、步骤切换、保存和提交状态变化给予轻微且有方向的反馈。
- 搜索、筛选和键盘操作立即响应，不做整表错峰入场。
- 快速切换取消上一段动画，不能锁页面等待动画结束。
- 系统和手动减少动态设置统一生效，关闭位移后所有功能仍可使用。
- 保留输入法组合、焦点和列表返回位置。
- 保存中、失败、冲突、关闭任务均提供具体、可执行的下一步。
- 不做自动播放背景动画、悬浮装饰、炫技图谱或长启动动画。

## 7. 执行顺序

### 阶段 A：先落地可评审的新视觉切片

1. 核对分支、代码和已有变更，检查本地预览，保存当前桌面与手机截图。
2. 按新规格更新 `DESIGN.md`，明确用户新偏好取代旧纸张方向。
3. 先制作“教师工作台 → 学生证据 → 准备跟进”和一个学生任务页面，使用已有虚构内容，检查内容密度与投屏可读性。
4. 用浏览器截图自检，确认新风格实际落实，再扩展到其他页面。不要先完成大量后端工作后才检验视觉。

### 阶段 B：迁出分析与持久化事实

1. 抽离内容、统计、推荐和导出服务，维持现有结果可复算。
2. 扩展独立教学状态并迁移旧练习，覆盖失败回滚与恢复。
3. `main.py` 改为应用装配，兼容入口调用新服务。

### 阶段 C：打通最小真实任务链

1. 教师建立历史学习回顾，核对依据。
2. 从建议准备任务，确认对象和内容后发布。
3. 学生查看待办、阅读材料、保存草稿、刷新恢复、正式提交。
4. 教师查看提交并反馈，学生查看结果或再次尝试。
5. 同范围报告与机读导出，前端分模块接入。

### 阶段 D：比赛展示与验证

- 提供一条约 3–5 分钟能够讲清的演示路线：问题 → 依据 → 教师安排 → 学生完成 → 后续反馈。
- 可以在独立本地数据空间中载入演示场景，必须标注演示；不删除或覆盖使用中的数据库，不编造已提交或已完成记录。
- 功能入口保持日常教学逻辑，演示辅助操作收在帮助或设置中。
- 优先保障离线运行、刷新恢复和明确空状态，不把外部模型作为必需条件。

## 8. 验证与验收

### 8.1 自动化测试

- 运行并保留当前 17 项回归，保证统计、证据不足、材料引用、导出、旧练习兼容及网络边界不退化。
- 新增任务草稿不可见、发布冻结、学生归属、草稿恢复、提交后反馈、教师要求重交、关闭后拒绝新提交、重复请求、版本冲突和保存回滚测试。
- 迁移、重复迁移、缓存清空、重启、备份恢复均用临时数据库测试。
- 导入应用前隔离数据目录，避免模块级 `app = create_app()` 触碰本机数据库。
- 检查学生接口没有泄露参考答案或其他学生记录；本地演示身份的局限如实说明。

### 8.2 浏览器完整流程

```text
教师查看学习情况
  → 核对学生
  → 保存任务草稿
  → 确认发布
  → 预览对应学生任务
  → 学生保存 / 刷新 / 提交
  → 教师反馈
  → 学生查看结果或继续尝试
```

验证 1440×900、1366×768、390×844 和 125% 缩放；检查中文组合输入、键盘焦点、返回位置、连续切换、减少动态、错误重试和冲突状态。

### 8.3 成果一致性

- 页面、报告和导出保持同一班级、学生、回顾范围、数据版本与证据引用。
- 未开始、进行中、已提交、已完成是不同状态。
- 阅读确认和客观题答对不冒充教学效果。
- 样例文件不能宣称为已完成正式赛事成果。

### 8.4 交付与 Git

- 更新 README、本地部署说明、`DESIGN.md` 和 `docs/decisions-teaching-flow.md`。
- 附新旧桌面与手机截图、可执行演示步骤、实际测试结果、已完成范围及限制。
- 用户全局已授权：修改验证完成后按 `commit-sentinel` 预检，只暂存相关文件，自动提交并推送当前开发分支，核对远端提交与文件内容。
- 不提交赛事原件、数据库、密钥、个人信息与截图运行产物。

## 9. 最终验收标准

第一次接触项目的人能够快速找到当前任务。教师看得懂为什么安排、接下来要处理谁；学生知道现在做什么、怎样提交、何时收到反馈。

比赛展示时，主要内容在正常缩放下清楚可读；观众能够沿着“问题、依据、安排、完成、反馈”理解项目价值，而不需要先理解数据集结构或系统技术实现。
